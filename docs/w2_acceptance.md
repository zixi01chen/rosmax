## 口径变更（2026-10-27 晚，用户要求）

压测消息从自定义 `rosmax_common/TestMessage` 切换为公开标准类型 **`std_msgs/msg/String`**：
- 时延协议：`data` 前 42 字节定长文本头 `<seq 20位>|<send_ts 20位>|`，其余 'x' 填充；payload_size 参数 = 整个字符串字节数（须 ≥42）
- 任何 ROS2 工具可直接 `ros2 topic echo /rosmax/live_0` 查看
- **历史 T1-01/T1-02 数据为 TestMessage 口径，与 String 口径不可直接对比**（序列化路径不同）；String 口径的首轮基线待独占窗口重测
- 本轮功能验证：3组×200Hz×1KB String 零丢包、100% 解析成功、面板/驱动/发现/动态拓扑全链路兼容（STATS 格式未变）

## 规模验证（2026-10-27 晚，组容器架构 mesh_group）

**架构**：一组一进程（组内 N 逻辑节点共享 DDS participant）。1000 节点 = 100 进程/100 participant——进程模型（一节点一进程）在此板不可行（participant 数 × 20-40MB 内存 + 发现风暴双重爆炸）。

| 规模 | 话题数 | 结果 |
|---|---|---|
| 1×3 | 6 | p50 52-84μs，rate 精准 200Hz ✓ |
| 4×2 | 8 | POST 生效 ✓ |
| 10×10 | 900 | rate 中位 97Hz（配置 100），零丢包，p50 ~590μs ✓ |
| **100×10（1000 节点）** | **9000** | **全部匹配成功**；内存 22.5/24.1GB 贴顶；发现风暴 load>200；数据面被挤压（rate 2Hz/10Hz，p50 ~15ms） |

**结论**：
- 组容器架构支持 1000 节点拓扑（9000 话题全匹配、进程零崩溃）
- 此板（24GB）默认发现配置下的**稳定运行上限约 300-600 节点**；1000 节点贴资源边缘
- 1000 节点稳定运行的三条路径：① FastDDS Discovery Server（消除 multicast 风暴，设计文档 W4 预留）② 降 history depth / best-effort ③ 多板分组（DDS 天然跨机，机器人系统真实形态）

**运维教训**：运行中二进制不可覆盖（Text file busy）→ 推送前必须停压测；100 组进程销毁会引发 sshd 无响应（load>200），降规模后等待恢复。

## 容量模型与充分测试（2026-10-29，组容器架构实测，板 .23 共享负载 load 5~10）

### 修复的三个大拓扑障碍
1. **fd 耗尽**：50 节点组 ≈ 4900 socket，默认 ulimit -n 1024 直接炸 → live_headless/topology 启动前 `ulimit -n 65535`
2. **rosout 放大**：每条 STATS WARN 都会发布到 /rosout（2450 行/s 统计 = 额外 2450 msg/s 话题流量）→ 改 fprintf 直写
3. **统计间隔**：大拓扑每秒 2450 行统计自身成为负载 → 间隔随规模缩放（max(1s, ceil(话题数/250))）

### 容量模型（实测归纳）
- **单组进程吞吐上限**：~2500 msg/s（板共享负载下，每消息 ~400μs 全链路成本）～60k msg/s（空载、延迟劣化到 ms 级）
- **μs 级延迟的配比规则**：每组 N×(N-1)×rate ≤ 20,000 msg/s（如 1×3@200Hz=1.2k ✓、10×10@100Hz=90k 全板尚可、1×50@200Hz=490k ✗ 20 倍超载）
- **全板总吞吐**：≤ 90k msg/s（1KB）可保持 rate 贴近配置值；超限后 rate 自动降速、p50 进入 ms 级
- **fd 前置条件**：ulimit -n ≥ 65535（已内置启动脚本）
- **1000 节点**：拓扑可达（9000 话题全匹配）；稳定运行需 Discovery Server 或多板

### 面板容量预警
总吞吐卡片 >50k msg/s 黄色、>100k msg/s 红色——超过即意味着 rate 将自动降速、延迟进入 ms 级。

## 过载保护（2026-10-29 追加，"反反复复界面空白"的根因修复）

**故障循环**：大拓扑过载（如 1×50@200Hz=49 万 msg/s，超单进程容量 5~20 倍）→ 节奏器超期补发分支无 sleep、以极限速率持续发布 → 整板负载 100+ → **sshd 饿死 → 监控通道（SSH 拉取）同归于尽 → 面板空白** → 重试再过载，循环往复。

**修复**：mesh_group 节奏器超期跳拍后**必须睡到下一个未来节拍**（兜底 1ms 间隔）——发布速率被钳制在 ≤ 配置频率，绝不超过。过载时表现为诚实的降级数字（rate 下降、p50 上升），板子、ssh、面板全部存活。

**实测验证**（1×50@200Hz 过载场景）：进程存活、板负载钳制在 10、SSH 全程可用、面板 2449 行实时更新、rate 中位 32Hz（降速可见）、p50 247μs·ms 级诚实呈现。

**容量速查**（面板总吞吐卡片变色预警已内置）：
- 绿色（≤5 万 msg/s）：μs 级延迟区间——例 1×3@200Hz、10×10@10Hz、1×50@8Hz
- 黄色（5~10 万）：延迟开始劣化但仍稳定——例 10×10@100Hz（rate 97Hz 实测）
- 红色（>10 万）：过载区——rate 自动降速、延迟 ms 级，监控通道仍存活但数字仅作趋势参考

## 面板交互与大组建立期（2026-10-29 补充）

**渲染 v5**：排序变化 = 行级移动（不拆表、零闪烁）；数值原位刷新；丢包率卡片+列；拓扑变更 = 全删重建（用户确认语义）+ writer 15s 宽限（切配置窗口不闪零）。

**1×50 建立期特征（重要预期管理）**：
- 点应用后 **2~5 分钟**为端点创建 + 发现收敛期（2450 端点相互匹配），期间面板行数会从 0 逐步涨到 2450——这是正常建立过程，不是失败
- 收敛后：rate ~8Hz/话题（配置 10Hz）、p50 ~88ms、零丢包
- **频率配比**（1×50 组内容量上限 ~2500 msg/s）：200Hz ✗ 严重超载；10Hz ⚠ 建立慢但可运行；**≤5Hz ✓ 推荐档**

**运维**：writer 保活并入 topology ensure（幂等）；面板重启不再触碰板端压测（解耦）；面板 ssh 对板重启换钥匙免疫。
